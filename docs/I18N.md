# Strings and formatting in OpenHamShack Remote

The family's rule is in openhamshack `docs/contract/I18N.md`: no
user-visible text in code, English as the source language, whole sentences
with placeholders, plurals through the platform's plural support, numbers
and frequencies through the shared formatter. The beta ships English only;
this page is how Remote follows the rule today.

## Where the English lives

| App | Catalog | In code |
|---|---|---|
| Android (phone, tablet, TV) | `android/app/src/main/res/values/strings.xml` | `stringResource(R.string.x)` in Compose, `pluralStringResource(R.plurals.x, n, n)` for a count, `LocalResources.current.getString` outside composition |
| iPad, iPhone, Apple TV | `ios/Shared/Localizable.xcstrings`, one String Catalog for both apps | SwiftUI literals (`Text("…")`, `Button("…")`) are already keys; `String(localized: "…")` for any text built as a `String`; `Text(verbatim:)` only for data |

OpenHamShackKit (the Swift package) has no catalog yet: its few sentences
(error descriptions) are M3 work, and need `defaultLocalization: "en"`
and a catalog inside the package when they move.

### Adding a string on Android

1. Add it to `strings.xml` in the group for its screen (`boxes_`,
   `signin_`, `settings_`, `tv_`, `qo100_`; `common_` for words that mean
   the same everywhere). Whole sentence, numbered placeholders (`%1$s`,
   `%1$d`), an XML comment when a translator needs to know what a
   placeholder holds. Escape apostrophes (`\'`).
2. A count is a `<plurals>` with at least `one` and `other`, used with
   `pluralStringResource` - never `if (n == 1)`.
3. Never join translated fragments into a sentence. Separate phrases
   joined by the app's ` · ` separator are fine (each is whole); `"PIN for
   " + address` is not (`stringResource(R.string.tv_pin_for, address)`).
4. A pure function that decides what to say (and is unit tested) returns a
   state, and a composable says it: `qo100State` and `qo100StateText` in
   `ui/Qo100Tune.kt` and `ui/I18n.kt` are the pattern.

### Adding a string on Apple

1. Write it in the code: a SwiftUI literal, or `String(localized: "…")`
   where the text is a `String` (a ternary of two literals, a `??`
   fallback, an error sentence, anything stored). Whole sentences: the
   PIN sheet has one sentence for iPhone and one for iPad rather than
   `Device.This` spliced into one.
2. Build both apps into one derived-data folder, then merge what the
   compiler extracted into the catalog and commit it:

   ```sh
   export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
   xcodebuild build -project OpenHamShackRemote.xcodeproj -scheme OpenHamShackRemote \
     -destination 'generic/platform=iOS Simulator' -derivedDataPath <dd> -clonedSourcePackagesDirPath <spm>
   xcodebuild build -project OpenHamShackRemote.xcodeproj -scheme OpenHamShackRemoteTV \
     -destination 'generic/platform=tvOS Simulator' -derivedDataPath <dd> -clonedSourcePackagesDirPath <spm>
   tools/sync-strings.sh <dd>
   ```

   xcodebuild extracts but never writes the catalog (only the IDE does),
   hence the script; it refuses unless both apps were built, because a
   sync marks every string it did not see as stale.
3. The catalog is in `Shared/`, so it is a resource of both targets with
   no project change (`tools/genproject.py` explains). An English-only
   catalog compiles to no `en.lproj` at all - Xcode only emits tables that
   differ from their keys - so do not look for one in the built app until
   a second language exists.

## The check

`tools/i18n.py check` runs ohs-libs' `shack-i18n-check` over the whole
repo (Android and Apple sources, both catalogs) from the pinned wheel in
`tools/vendor/`, then applies the baseline. It needs python3 3.11 or later.

- **Android:** the Gradle task `i18nCheck` runs it, and every test task
  and `check` depend on it, so `./gradlew testDebugUnitTest` fails on a
  finding. This is the run that covers the Apple sources too.
- **Apple:** the build Mac's python3 is 3.9, which the check cannot run on
  (it needs `tomllib`), so nothing on the Mac runs it. The Swift and
  catalog half is checked by the Android build and by running it by hand
  anywhere with a newer Python: `python3 tools/i18n.py check`.
- `.i18n-check.toml` excludes only what never reaches a user (developer
  tools, tests, the Android debug source set, the iOS `#if DEBUG` launch
  arguments), each with its reason.
- Android Lint's `HardcodedText` and `SetTextI18n` are errors
  (`android/app/lint.xml`) for the day an XML layout or TextView appears.
  (`lintDebug` is not part of the normal run: it already fails on an older
  `RememberInComposition` error in `TvQo100.kt`.)

What it cannot see: the Swift scanner's sinks are UIKit and
`Text(verbatim:)`, so a `String` handed to `Text(_:)` is not a finding, and
in Kotlin only literals passed straight to a sink are (a literal returned
from a helper and shown later is not). It also warns about catalog keys it
cannot see used - SwiftUI `Button`, `Label`, `Toggle` and interpolated keys
- which are real keys; warnings never fail the run.

### The baseline and the allow-list

- `i18n-pending.txt` is the baseline: every literal that was in the code
  when the check arrived, one line per file and literal, written once with
  `tools/i18n.py baseline --add-new` after the first slice was converted.
  Converting one means moving it to the catalog and running
  `python3 tools/i18n.py baseline`, which drops lines that no longer match.
  A line that matches nothing fails the check, so the count only falls.
  `--add-new` is never for silencing a new finding.
- `i18n-allow.txt` is for literals that are not language (`glob |
  "JSON literal" | reason`); the reason is required and an entry that
  matches nothing fails. Mode names and `QO-100` are already in the tool's
  shared list.
- A converted string is in neither file.

## Frequencies: ShackFormat

Frequencies go through ShackFormat (I18N.md §4.1: kHz or MHz, the locale's
decimal separator, never grouped, a no-break space before the unit). So far
one display uses it on each platform: the QO-100 signal rows
(`downlinkText` in `android/.../ui/Format.kt`, `Tuning.downlink` in
OpenHamShackKit); the rest of the app's `mhz()` texts are M3 work.

Both platforms carry a copy of the ohs-libs port rather than depend on
ohs-libs, because Remote builds from this repo alone and the formatter is
one dependency-free file:

| Copy | From ohs-libs | Proved by |
|---|---|---|
| `android/core-candidates/src/main/java/com/openhamshack/i18n/ShackFormat.kt` (shared by :app and the Icom kind) | `kotlin/shack-i18n/src/main/kotlin/com/openhamshack/i18n/ShackFormat.kt` | `FormatVectorsTest` (`testDebugUnitTest`) over `src/test/resources/i18n/format.json` |
| `ios/OpenHamShackKit/Sources/OpenHamShackKit/ShackFormat.swift` | `swift/Sources/ShackFormat/ShackFormat.swift` | `FormatVectorsTests` (`swift test` in `ios/OpenHamShackKit`) over `Tests/OpenHamShackKitTests/Fixtures/i18n-format.json` |

To refresh: copy the library file over the copy below its header, update
the commit in the header (`git -C ~/ohs-libs log -1 --format=%h -- <path>`),
copy `spec/vectors/i18n/format.json` over both fixtures and update their
commit too, then run both test suites. A vectors `version` change means the
test itself may need the library test's changes.
